### 1.2 参照实现的真实完整度（来自本仓库功能清单与实测）

- 读写的地图文件只有 9 个：`w3e / wpm / doo / war3mapUnits.doo / w3i / wts / wtg / wct / j`。
- **不读不写**：`war3map.imp`（导入管理器已退化成文件浏览器）、`war3map.mmp`（小地图图标）、`war3map.shd`（静态阴影，`ShadowMap` 是死代码）、`war3mapMap.blp`（缩略图）→ 改地形后小地图与阴影不更新。
- 已知缺陷（已复核，写在 `.workbuddy/memory`）：
  - `Triggers::build_trigger_data()` 末尾直接写盘，而 `load()` 会调它 → **每次打开地图都重写一遍 `war3map.wtg`**，往返不一致时会自毁（实测过一次启动即崩，元凶就是被改坏的 wtg）。
  - 脚本生成器系统性残缺：可破坏物/物品创建函数生成为空、`.doo` 字段错位、`SetTeams` 与官方不一致。
  - `_Locales\<lang>.w3mod\war3map.wts` 优先级高于根 `war3map.wts`，而编辑器只写根表。
  - `Terrain::pathing_options` 全工程无加载/保存，重开地图即丢。
  - 笔刷寻路重算每笔无条件清 `0x4E` 位，开关=关是「擦掉」而不是「保持原样」。

**结论：不能把 HiveWE 0.6 当作「正确性基准」直接照抄。** 结构、字段顺序、渲染参数可以抄；业务逻辑（触发器生成、寻路重算、多语言字符串）要以官方 World Editor 的输出为准。

## 2. HiveWeGodot 做了什么，为什么只能参考

### 2.1 它的路线

把 HiveWE 上游 C++ 核心原样编译，用 `native/include/` 的同名转发头骗过 Qt 依赖，再把 Vulkan 渲染用 `HIVE_HEADLESS` 编译期短路，最后通过 24 个函数的 C ABI 给 Godot C# 前端用。核心源码「一行不改」。

### 2.2 结构性代价（这是不能复用的根本原因）

| # | 问题 | 具体表现 | 代价 |
|---|---|---|---|
| 1 | **状态所有权倒置** | 地图数据住在 C++ 核心，Godot 只是镜像；每个新功能都要新增 C ABI 函数并手工同步 | 24 个函数只是起点，功能越多桥越厚；每次交互跨 ABI 拷数据 |
| 2 | **Qt 兼容层语义漂移** | `QRect::right()` 闭区间、`QString::arg` 替换规则、`QSettings` 一律返回默认值 | 「核心未改一行」反而制造了看不见的行为差异，排查成本远高于重写 |
| 3 | **Vulkan 死代码** | `render/` 3520 行保留编译，8 处 `HIVE_HEADLESS` 短路 | 一份永远不会执行的渲染实现，后续任何核心改动都可能触碰 |
| 4 | **替身库降级** | `CascLib` 所有函数返回失败、`SOIL2` 返回 nullptr | **1.31 / 重制版数据永远读不到**（本机客户端恰好是 1.31），DDS/TGA 贴图不可用 |
| 5 | **平台残留** | 为 Apple clang 去掉 C++20 模块、macOS dylib 签名 | 换到 Windows + 纯 C# 后这些工作全部作废 |
| 6 | **动画与性能折衷** | 单位按「模型 + 玩家」分组，共享时钟 12fps 重蒙皮；装饰物不播动画；几何体 alpha 不播；18k 实例未实测 | 视觉上明显「不是 War3」；改成逐实例又要重写渲染层 |
| 7 | **上游分叉** | 去模块化 + 补丁表，HiveWE 更新不能同步 | 锁定 commit，长期失去上游修复 |
| 8 | **功能缺口** | 对象编辑器无分类树/图标/搜索；触发器无变量编辑器；headless 下跳过 JASS 编译，触发器改动可能不落盘 | 表面上「都有窗口」，实际不可用于正经做图 |

### 2.3 可继承的资产（有价值的部分）

这些是「结论型知识」，与实现语言无关，直接写进新工程：

1. **四层纹理混合公式**（`Data/Shaders/terrain.fs`）：
   `color = mix(下层, 上层, 上层.a)`，逐层叠四次，顺序为 `a → b → g → r`；
   每个 corner 存一个 `uvec4`，每字节打包 `index | variation << 5`；
   ground 纹理走 `sampler2DArray`（17 个切片），17 号为「无」返回全透明。
2. **寻路叠加配色**：`(final&2)>>1, (final&4)>>2, (final&8)>>3`，alpha 0.25，`color*0.75 + overlay*0.5`。
3. **水面参数**：`min_depth = 10/128`、`deeplevel = 64/128`、`maxdepth = 72/128`，浅/深各一对 min/max 颜色，纹理数组 + 动画速率。
4. **坐标与高度语义**：物理高度用 `corners.height`，可视高度 `final_ground_height() = height + layer_height - 2.0`；两者只在 `layer==6` 时重合 —— 这正是笔刷偏移 1-4 格 bug 的根因（提交 `4ba7d79`）。新工程必须从一开始就用同一套高度定义。
5. **测试地图与预期数据**：`BootyBay` 193×97、7 种地面纹理、2011 个装饰物、61 个单位、18721 个高度点（HiveWeGodot 实测值）。可作为新工程的基准断言。
6. **踩坑清单**：MPQ 的 `(listfile)`/`(attributes)` 要跳过；`SFileFindFirstFile` 返回反斜杠；CASC 内部路径带 `war3.w3mod:` 前缀；StormLib/CascLib 的 `UNICODE` 宏必须与调用方一致（否则链接正常、运行时路径乱码）。

## 4. 从上一代得到的四条硬结论

1. **不要有第二个运行时。** 数据模型、格式解析、业务逻辑必须在 C# 里，Godot 只做「读数据 → 画/改」。没有 C ABI，没有镜像，没有同步。
2. **不要兼容层。** 任何「让旧代码原样跑」的适配层，最终都会变成不可维护的语义缝隙。
3. **参考实现要用在正确的地方。** 抄字段顺序、抄渲染公式、抄格式分支；不抄触发器生成、不抄寻路重算、不抄多语言策略。
4. **验收必须可执行。** 每个阶段都要有能在命令行跑出来的断言（字节一致、逐点高度一致、截图对比），不靠肉眼「看起来对」。
