## 2. BLP 的三个坑（都不是猜的，是读字节读出来的）

### 2.1 头后面固定有 1024 字节调色板，`mipOffsets` 多算了它

`Lords_Dirt.blp`（512×256）头 156 字节，之后 156..1180 是 1024 字节的共享调色板区。
`mipOffsets[0] = 1180`，而 JPEG 的 `jpegHeaderSize`（624）实际在 **156** 处。

- JPEG：`jpeg = data[160..160+624] + data[1180..1180+mipSize]`
- 调色板：调色板在 156，索引数据在 1180

一开始按 `mipOffsets[0]` 取，读到 `jpegHeaderSize = 17306624`（把 JPEG 像素当成了长度）。

### 2.2 4 分量 JPEG 是 BGRA，不是 CMYK

`SOF0` 里 `components = 4`、四个分量都是 1×1 采样（4:4:4）。Godot 内置的 stb_image
**不支持 4 分量**，Pillow 会按 CMYK 解释（颜色对但语义错）。

实测：四个通道均值 `200 / 153 / 111 / 22`。若按 RGB 解释是棕色泥土；若按 BGR 解释是蓝色。
**结论是 BGRA**——HiveWE 的 `BLP.cpp` 里那句 `TJPF_CMYK // Actually BGRA` 就是这个意思。

第 4 分量不是可靠的 alpha（地形贴图均值只有 22，当 alpha 会让整张图透明），地形直接置 255。

### 2.3 只能自己写解码器

因为不能做 YCbCr 转换（前三个分量本来就是 RGB），所有托管库（ImageSharp / System.Drawing）
都会替你做色彩空间转换，反而错。于是写了 `JpegBaselineDecoder`（约 500 行）：

- 只支持 SOF0 基线、8bit、无 restart marker（实测 60 张地形贴图 100% 符合）
- MCU 遍历支持 1..4 分量与任意采样因子
- 4 分量按 BGRA 输出，3 分量按 YCbCr 转 RGB，1 分量灰度
- IDCT 用行列分离的浮点实现，正确性优先

## 3. 地形高度：漏掉 `layer_height` 会让整张图沉到水下

```
世界高度 = (raw - 8192) / 512 + layer_height - 2      // 单位：格
         × 128                                        // 换成世界单位
```

`layer_height = misc & 0x0F`，这张图里的分布是 `6:6394, 4:5147, 2:3221, 8:2584…`，
也就是地形被抬高了 2–6 格。漏掉它时，地形高度只有 `-0.5..2.1` 格，而水面是 `1.3` 格，
结果整张地图泡在水里。加上之后陆地正常露出。

水面高度：`(water & 0x3FFF - 8192)/512 + Water.slk["<tileset>Sha"].height`
（洛丹伦夏的偏移是 `-0.7`，于是这张图的水面 = 2 - 0.7 = 1.3 格 = 166.4 单位）。

## 4. 地表贴图：「八向连续」到底是什么

一张地表 BLP 是 **512×256 = 8 列 × 4 行个 64×64 小块**，但左右两半**用途完全不同**（实测 alpha）：

| 位置 | alpha | 用途 |
|---|---|---|
| 右半 c4–c7（16 块） | 全部 255 | **纯色块**，负责纹理变化 |
| 左半 c0–c3（16 块） | 0–255 渐变 | **遮罩块**，一块对应一种「四角组合」，负责格子之间的柔和过渡 |

左半 16 块的索引正好等于「这一格四角里，哪些角是这种地表」的 4 位掩码
（bit0=右下、bit1=左下、bit2=右上、bit3=左上），所以：

- 四角都是同一种地表 → mask = 15 → 左半第 15 块，alpha 恰好是 255（完全不透明）
- 只有左上角是这种地表 → mask = 8 → 第 8 块，alpha 是「只剩左上角」的渐变遮罩

**这就是 War3 地表在格子之间能平滑过渡的原因**，也是所谓「八向连续」的实现方式：
每个 tile 不是一个硬邦邦的方块，而是「底色 + 若干层带遮罩的边缘」叠出来的。

我们的做法：

| 层 | 层号 | 说明 |
|---|---|---|
| 底层 | `BaseLayer(最小 tileID) + VariationLayer(左下角 variation)` | 纯色块，提供纹理变化 |
| 第 2–4 层 | `BaseLayer(tileID) + mask` | 遮罩块，mask 就是那 4 位 |

shader 里混合必须用**上层**的 alpha：

```glsl
vec4 c = texture(ground_texture, vec3(UV, layer.x));
vec4 l1 = texture(ground_texture, vec3(UV, layer.y));
c.rgb = mix(c.rgb, l1.rgb, l1.a);   // ← 用上层的 alpha 当比例
```

**HiveWE 这里是错的**：它写的是 `color = color * color.a + next * (1 - color.a)`，用**当前层**的 alpha。
底层是纯色块（alpha=1），乘完下一层就被乘 0 了，所以它的四层叠加实际不生效，
格子之间只剩硬边——照它抄会得到一块块拼贴的草地。

## 4.0.1 切成 texture array

把每个 64×64 小块切成 `sampler2DArray` 的一层（每张地表固定占 32 层 + 第 0 层是全透明黑），
采样时 UV 在格内取 0..1：

- **mip 不再串色**。以前整张 512×256 当一层、UV 落在 1/8 子区间，拉远时 mip 把隔壁小块平均进来，草地糊成一片云。
- 每格顶点带**四层**的绝对层号（`CUSTOM0` 的 xyzw），shader 直接拿它当数组层号。
- 第 0 层是全透明黑，给「这一格只有 1–3 种地表」时的空位用（对应 HiveWE 的 17 号黑纹理）。
- 加空层时必须**一起生成 mipmap**，否则 `CreateFromImages` 尺寸不一致会整张失败，画面上是品红棋盘格。

## 4.1 着色：和 HiveWE 对齐的是「不做线性化」

HiveWE 的地形是 `color.rgb *= clamp(dot(normal, light) + 0.45, 0, 1)`，**直接在 sRGB 数值上乘**，
没有色调映射、没有辐照度、没有 gamma 校正。我们原来是正确的线性 PBR 管线（太阳 + 环境光 + Filmic），
出来的草地又亮又艳，和 HiveWE 差得远。现在的做法：

| 项 | 处理 |
|---|---|
| 材质 | `unshaded`，`fog_disabled`；地表/悬崖/水面都自己算颜色 |
| 光照 | 顶点上算好 `clamp(dot(n, L) + 0.45)` 塞进 `COLOR.rgb`，L 取 HiveWE 的 `(-0.3, 0.25, -0.3)`（Y 向上） |
| 法线 | `normalize(vec3(hL-hR, 2, hD-hU))`，竖直分量是 2 而不是 1，坡度光差才和 HiveWE 一致；高度只用 **w3e 原始高度，不含 layer_height**（HiveWE 读的就是不带层高的高度贴图），否则坡道/悬崖口会被算成陡壁直接压黑 |
| 输出 | `ALBEDO = srgb_to_linear(贴图 * COLOR)`，抵消 Godot 最后那次 linear→sRGB |
| 环境 | `ToneMapper.Linear`，关雾 |

实测：画面上的草色 `(23,108,16)`，贴图该格均值 `(33,114,21)` × 遮挡系数 0.95 ≈ `(31,108,20)`，
两者对得上，说明 sRGB 空间那条链路是通的。

## 4.2 悬崖（2026-11-05 晚补）

War3 的悬崖不是「拉伸出来的斜面」，而是**逐格的 MDX 模型**：`Doodads/Terrain/Cliffs/Cliffs????.mdx`。
文件名四个字母是四角相对最低层的高度差（A=0、B=1、C=2、D=3，顺序 bl、tl、tr、br），末尾一位是变体号。
这里按 HiveWE 的 `update_cliff_meshes` 复刻：

| 步骤 | 做法 |
|---|---|
| 判定悬崖格 | 四角 `layer_height` 不全相等（HiveWE 的 `corner.cliff`） |
| 抠地面 | 悬崖格的地面整块不画，交给模型；四角都是斜坡的「斜坡入口」例外 |
| 选模型 | `'A'+bl-base, tl, tr, br`，变体号取 `cliff_variation`，模型不存在就往下退到 0 |
| 摆放 | 模型 1 单位 = 1 世界单位，横向占满一格；MDX 是 Z 向上 → `(x, y, z) → (x, z, y)`，**不用反绕序** |
| 竖直 | 逐顶点采样该格的地表高度（四角原始高度双线性插值 + 最低层），模型自带的 z 表示高出地面多少 |
| 贴图 | 角点的 4 位悬崖索引 → w3e 的悬崖集合 id → `CliffTypes.slk` 的 texDir/texFile → texture array 层 |
| 着色 | 和地面同一套：每格用四角平均法线算一个系数，乘在贴图上；不开背面剔除（HiveWE 也没开） |

踩到的几个坑：

- **绕序**：MDX 的三角形在这个映射下和 Godot 的正面约定一致，先按「镜像要反绕」做，结果整个悬崖被背面剔除掉，
  画面上只剩抠掉地面的黑洞。
- **竖直位置**：一开始用左下角一个高度铺满整格，格内四个角高度不同时崖底会悬空/穿地，出现沿崖顶的
  黑色三角缝。改成逐顶点采样地面后缝隙消失。
- **背面剔除**：模型是开口的壳，关掉剔除才不漏底（HiveWE 全程没开 `GL_CULL_FACE`）。

## 4.3 水面（2026-11-05 晚改）

原来是「整张图一个平面 + 水位取众数」，河道、内陆湖会被海平面淹掉。现在按 HiveWE 的 `water.vs/fs` 逐格铺：

| 项 | 做法 |
|---|---|
| 铺法 | 只要一格四角里有任一角 `water` 标记就出这个格子，四个顶点各用自己角点的水位 |
| 水位 | `(w3e 水位 + Water.slk 的 height)`，洛丹伦夏偏移 -0.7 |
| 颜色 | 水深 = 水面 - 最终地面高度（含层高），到 0.5 格分界：浅水段 Smin→Smax、深水段 Dmin→Dmax，颜色端点全取 `Water.slk` |
| 透明度 | 颜色自带的 alpha 一起用（浅滩 10/255，深水 250/255），所以岸边几乎看不见、深海不透明 |
| 波纹 | 45 帧 `ReplaceableTextures/Water/WaterNN.blp` 打成 texture array，一格铺一次（暂时固定第 0 帧，没做动画） |
| 干燥角点 | w3e 里干燥角点的水位字段是残留值，直接会从草地里戳出一片水，所以压到地面高度、alpha 0 |

## 4.4 斜坡过渡（CliffTrans）与地面抠除

「生成坡道」刷出来的斜坡不是普通悬崖模型，而是 `Doodads/terrain/CliffTrans/CliffTrans????.mdx`，
**一个模型跨两格**（`AAHL` 跨 y 两格、`ALHA` 跨 x 两格）。名字里的字母：斜坡角点从 `'L'` 往回数（每差一层退 4 个字母），
平面角点从 `'A'` 往上数，正好能对上那 32 个文件。

地面的抠除不再照抄 HiveWE 的 `romp` 标记，而是**按模型顶点的实际包围盒**标记「这一格被盖住了」，
再据此抠地面。理由：斜坡模型跨两格，靠名字推锚点容易偏半格，用几何本身最稳（BootyBay 2400 个模型
对应抠掉 2425 格，对得上）。

## 4.7 相机高度上限

设置窗口的「相机最高高度」（默认 12000，范围 500–30000）约束的是**相机位置 Y**，不是目标点的高度。
`UpdateCamera()` 里当 `target.Y + offset.Y > MaxCameraHeight` 时按比例缩小距离，因此滚轮拉远、Ctrl 旋转、Shift 升降都会一起受约束。

实测：`--dist=20000` 时被压到 `dist=16181 / camY=12000`，正好卡在上限；`--dist=5407` 时 `camY=4250`，不受影响。

## 4.7.1 坐标系：直接换轴 = 左右镜像

HiveWE 是 **z-up 右手系**（x 向右、y 向前、z 向上），Godot 是 **y-up**。
把地图 `(x, y)` 直接映射成世界 `(x, z)`、高度映射成 y，即 `(x, y, z) → (x, z, y)`——
**交换两个坐标轴是一次反射变换（行列式 -1）**，手性翻过来，画面上就是**左右镜像**。

这个错误在截图对比里非常隐蔽：两张图的岛屿、海岸线「看起来都对」，但用
`tools/mirror_check.py` 一测就露馅——把我们的图水平翻转后，水域重合度从 62.7% 跳到 83.8%。

修法（`AddVertex` / `AddWaterVertex`，一处收口）：

```csharp
st.SetNormal(new Vector3(-normal.X, normal.Y, normal.Z));   // 法线 x 跟着反
st.AddVertex(new Vector3(-position.X, position.Y, position.Z)); // 世界 x 取反
```

连带要做三件事，否则会掉面或者「看向地图外面」：

| 连带项 | 原因 |
|---|---|
| 每个三角形的后两个顶点对调 | 镜像后绕序反了，`cull_back` 会把正面剔除掉，地形直接消失 |
| 相机 target 的 x 取反 | target 和顶点必须在同一个坐标系里 |
| **占位地形 / 占位水面 / 笔刷环也要镜像** | 它们也是场景里的几何。只改真实地图时，程序启动后相机会看向地面范围之外，且 `ClampTarget` 的 x 上界是 0，拖也拖不过去（表现就是「默认场景相机位置不对，挪不到地图中间」） |

坐标夹取同样会踩坑：`ClampTarget` 的 x 范围是 `[-宽 * 128, 0]`，不是 `[0, 宽 * 128]`；
格坐标 ↔ 世界坐标统一走 `MapToWorld` / `WorldToMap` 两个函数，不要再手写 `x * CellSize`。

## 4.7.2 相机中心要用整数除法

`Camera::reset` 里是 `position = glm::vec3(map->terrain.width / 2, map->terrain.height / 2, 0)`，
`width` 是 `int`，所以 193/2 得 **96**，不是 96.5。

用 96.5 会让整幅画面偏**半格**（1600 宽的视口上约 22 像素）。
`tools/water_iou.py` 会直接给出最佳平移量——改之前是 `dx=-22`，改完变成 `dx=0`，重合度 83.4% → 87.2%。

## 4.7.3 另外两个「看起来对、其实错」的点

| 项 | 现象 | 原因 |

## 4.8.1.1 四边形三角剖分：对角线的方向要和 HiveWE 一致

War3 的地面是「一格一个四边形」，每个四边形再切成两个三角形。切哪条对角线会影响坡面形态：

| | 切法 |
|---|---|
| HiveWE（`Utilities.h` 的 `quad_indices`） | `{(0,3,1),(1,3,2)}`，即沿 **p10–p01 反对角线** |
| 我们（改之前） | 沿 **p00–p11 主对角线** |

同一个四边形在坡度过渡处，两条对角线会切出「屋脊」和「凹谷」两种完全相反的形状，
肉眼看到的就是「一边是直线折面、另一边是平滑曲面」。改成和 HiveWE 相同的反对角线后，
同一机位的分块差异降到原来的一半左右，默认视角水域重合度 89.5% → **89.8%**。

注意：改完对角线后绕序也变了，每个三角形要按镜像后的方向重新排列，否则整片地面会被背面剔除（画面全黑）。

## 4.8.1.2 斜坡：两格半层的斜面，不是曲面

War3 的斜坡**不在着色器里算**。地表是一整片 1×1 的四边形实例网格，`terrain.vs` 只按顶点所在角点
`texelFetch` 一次高度贴图，`terrain.fs` 只做 4 层地表混合 + 一个固定方向光，
既没有位移贴图也没有曲面细分——所以斜坡一定是**分段平面**，几何上不可能弯曲。

真正决定坡度的是 `Terrain::update_ground_heights()` 里的这一句：

```cpp
if (is_corner_ramp_entrance(...)) { ramp_height = 0.5f; goto exit_loop; }
ground_corner_heights[...] = corners[i][j].final_ground_height() + ramp_height;
```

即：**「斜坡入口格」（四角 ramp 标志全真、对角层高不一致）的底层角点抬高 0.5 层**。
一层高差因此摊到两格上、每格半层，得到约 24° 的等斜率斜面；起坡和收坡各有一个折点，中间是直线。

给 HiveWE 加了 `--probe`（沿格坐标直线打 Bullet 射线，同时算一遍渲染三角面高度）实测 x=60 的剖面（单位：格）：

| y | 渲染面 | 碰撞面 | 说明 |
|---|---|---|---|
| 34.0 | 1.1172 | 1.1172 | 起坡点 |
| 34.5 | 1.3408 | 1.3408 | 斜率 0.4473 |
| 35.0 | 1.5645 | 1.5645 | 折点，斜率换成 0.4355 |
| 35.5 | 1.7822 | 1.7822 | |
| 36.0 | 2.0000 | 2.0000 | 收坡点 |

两点结论：碰撞面和渲染面**逐点一致**（Bullet 高度场用的也是同一条反对角线），
斜坡是两段直线而不是曲线。

**我们漏了这半层**：`GroundWorld` 只算 `height + layer - 2`，于是斜坡压缩成一格、约 43°，
同一位置比 HiveWE 低 64 世界单位。副作用很明显——斜坡下段掉到水面（166.4）以下
（(60,35) 地面 136 vs HiveWE 200），水面把整条斜坡糊住，还多出一条笔直的水岸线。

修法：`CornerWorld(terrain, x, y)` = `GroundWorld(corner) + RampLift(terrain, x, y) * CellSize`，
`RampLift` 遍历包含该角点的四格，只要有一格是斜坡入口且本角点是它的底层角点就返回 0.5。
施加在**地形网格顶点**和**水面深度着色**上（HiveWE 的 `water.vs` 绑的也是带半层的 `ground_corner_height`）；
`InterpolatedHeight`（相机高度、抠地面采样）保持不加，和 HiveWE 的 `interpolated_height()` 一致。

同机位效果：与 HiveWE 的平均灰度差 13.8 → **7.6**，水域重合度 25.1% → **41.9%**；
默认视角 89.8% → **90.3%**。BootyBay 全图共 83 个斜坡入口格、93 个需要抬升的角点。

## 4.8.2 小地图方向：纵向要翻，横向不翻

小地图是按 w3e 逐格取色画出来的，方向必须和 3D 视图一致：相机在 -z 看向 +z，
所以**世界 z 越大越远、越靠画面上方**；而图片第 0 行也是上方，于是行号要倒着数：

```csharp
int ty = (drawH - 1 - py) * tilesY / drawH;   // 不是 py * tilesY / drawH
```

横向不用翻：格 x 增大 → 世界 x 减小 → 屏幕向右，图片列号和格 x 同向。
（世界 x 是镜像的，但相机的右向量也是 -x，两次取反抵消。）

验证方式不靠眼睛，直接和 w3e 的水位标记做相关性（`--minimap-dump=` 导出小地图 PNG）：

| 方向 | 正常相关系数 | 翻转后相关系数 |
|---|---|---|
| 纵向 | **0.998** | 0.159 |
| 横向 | **0.998** | 0.452 |

## 4.8.3 地面抠除：先看 cliff 位，再看模型盖没盖满

**主规则和 HiveWE 一样：悬崖格的地面整块不画。** HiveWE 在 `update_ground_textures` 里给
`corners[i][j].cliff`（四角层高不完全相同）的格子打上 `0x8000` 位，`terrain.vs` 见到就把
四个顶点丢到 `vec4(2,0,0,1)`（屏幕外），整格消失。

为什么必须抠：这种格子的四个角点跨了两个层高，地面四边形本身是个 **45° 斜面**，
留着它就会从竖直的岩壁里斜切出一块草地——表现就是「地表和悬崖的连接处」有块穿模的斜面。

补充规则（HiveWE 没有）：`covered[x,y]` —— 单个模型自己的三角形 16 个采样点**全部**命中才算盖满。
这是为了处理「模型确实把整格盖住、但这格不是 cliff 格」的情况。规则本身也改过三轮：

| 版本 | 做法 | 结果 |
|---|---|---|
| 1 | 模型顶点**包围盒** | 跨两格的 `CliffTrans` 把邻格也标成被盖住 → 地面挖掉、模型没铺到 → **纯黑方块** |
| 2 | 全图三角形汇总后按格采样（任一点命中即抠） | 隔壁模型的斜面误判 → 仍会挖洞 |
| 3 | **单个模型自己的三角形**，16 个采样点**全部**命中才抠 | 正常 |

两类特例保持原样：

| 情况 | 处理 |
|---|---|
| 斜坡过渡 `CliffTrans` | **不抠地面**。它只是贴在坡面上的薄片、本身不封闭，抠了就从缝里看到背景/水面（表现为水面里的深色三角楔形） |
| 斜坡本体（ramp entrance） | 不抠地面、不摆崖壁模型（见上一节） |

实测（机位 `--cam=-21759,1551,9375`）：只按 cliff 位抠之后，和 HiveWE 的平均灰度差
**5.31 → 1.47**，近黑像素占比 0.0020 与 HiveWE 完全相同（没有新挖出洞）；
默认视角 5.81 → 5.42，冒烟 33/33。全图抠掉 2413 格。

### 水面高度不要「压到地面」

曾经为了防「草地上冒水斑」，把没有水的角点水位夹到地面高度。结果在崖边水面被抬起来，
形成一条竖着的深色三角片——关掉水面看就是纯黑的洞。现在照 HiveWE 的 `water.vs`：
**一律用角点自己的 `water_height + offset`**。实测 w3e 里水位字段只有 0 和正常水位两个值，
都在地表以下，交给地形遮住即可。

改动后同一机位（`--cam=-17381,842,3253`）黑洞完全消失，默认视角水域 IoU 从 87.7% 升到 **89.5%**。

## 4.8.4 光照开关（对应 HiveWE 的 `render_lighting`）

HiveWE 的地形和悬崖共用一套假光照：固定平行光 `normalize(-0.3,-0.3,0.25)`，
片元里 `color.rgb *= clamp(dot(normal, L) + 0.45, 0, 1)`，`map->render_lighting` 为假时整段跳过。

我们照抄：两个 shader 各加一个 `uniform bool lighting_enabled`，Ribbon 的「光照」按钮
（原来只发 `Stub.Fire`）现在走 `LightingToggled` → `ViewportPanel.SetLighting()`，
把它写到所有已登记的地形/悬崖材质上；换地图时材质是新造的，`RegisterShadedMaterial()`
会把当前开关状态重新写进去，按钮状态和画面对得上。

因为光几乎顶光、外加 0.45 的偏置，平地只有约 4% 的变化（0.958），
关掉光照后主要是背光面和崖壁变亮；朝向背离光的崖面在开光照时会压到 0（纯黑），这点和 HiveWE 一致。

命令行验证用 `--no-lighting`（两边都有），同机位对比：我方开/关整幅差 3.44，HiveWE 4.07，量级一致。

## 4.9 这一轮修掉的四个真 bug

| Bug | 现象 | 原因 |
|---|---|---|
| **法线用了世界单位** | 坡面明暗被夸张，坡道口一片近黑 | HiveWE 的高度贴图存的是「格」单位 `(raw-8192)/512`，法线 `normalize(hL-hR, 2, hD-hL)`；我们拿世界单位（×128）去算，水平分量大了 128 倍 |
| **水深漏了层高** | 浅滩全被算成深水，一片深蓝 | HiveWE 水面着色器绑的是 `ground_corner_height`（含 `layer_height - 2`），我们用了不含层高的高度 |
| **斜坡入口完全不摆模型** | 「生成坡道」刷出来的台地一个崖壁都没有 | HiveWE 只在**抠地面**时跳过 ramp entrance，悬崖模型照摆（用 CliffTrans）；我们在悬崖循环里直接 `continue` 了 |
| **地表没走 `real_tile_texture`** | 悬崖脚下是普通草地，没有岩石/泥土带；blight 不显示 | HiveWE 会先把「附近有悬崖/斜坡的角点」换成该悬崖的 `groundTile`、把疫病角点换成 blight 贴图，再到角点自己的地表 |

```csharp
private static readonly string[] TerrainColumns = ["tileID", "cliffSet", ...];
private static readonly string[][] TerrainRows = [["Ldrt", "0", ...], ...];
public static SlkTable Terrain() => _cachedTerrain ??= SlkTable.FromRows(TerrainColumns, TerrainRows);
```

调用方只写 `War3Tables.Terrain()`，和以前 `SlkTable.Parse(War3Assets.Read(...))` 的返回值类型完全相同，
`FindRow / Get / GetInt / GetFloat` 一行没改。

**收益**：`assets/terrain/` 整个删掉，导出包不再需要任何“非资源文件”，`include_filter` 置空；
启动时省掉 35 次（实际用到 3 次）文件读 + SYLK 解析。

**代价**：改表要重跑 `python tools/slk2cs.py` 再编译（编译多 4 秒）。源数据直接读仓库根的
游戏安装目录（不在工程里，Godot 不导入、不导出）。

**校验**：`--table-check` 用反射把 35 张表逐张读一遍，打印行列数：

```
[TABLE] AbilityData rows=803 cols=95
[TABLE] DialogSounds rows=2230 cols=6
[TABLE] Terrain rows=177 cols=14
...
```

两处列数比源文件少（`T_SplatData` 20→2、`UnitWeapons` 79→78），原因是这些表的表头本身有空列名
（`T_SplatData` 20 列里 19 列没有名字），空列名在 `_columns` 字典里互相覆盖。
**数据没丢**（值仍然按列号存在行里），只是按名字查不到——这几张表目前没有用到。

同机位与改前逐像素相同（排圈差 0.00），导出包 355.4 MB、`悬崖 2400 / 地表 6/6 / 水面 4527 格`、
冒烟 33/33。

### 6.2 文本表 `.txt` → C# 字典

`war3/` 下 118 个 `.txt`（单位名、技能名、物品名、编辑器界面文字），
`tools/txt2cs.py` 转成 `Godot/assets/converted/Texts/`，**一个文件一个 partial 片段**：

| 项 | 数值 |
|---|---|
| 表 | 98 个（另 20 个没有键值，跳过） |

解析规则（三类表共用）：

```
// 注释行       → 跳过
[Section]      → 后续键值归到这一节
KEY=值          → 第一个 = 之前是键，之后原样保留（值里有 |cffffcc00 颜色码、逗号、等号）
```

段名非空时键拼成 `Section.KEY`，取值就一句：

```csharp

```

### 6.4 `.fdf`（界面布局）：评估过，**暂不转**

`war3/UI/FrameDef/` 下 74 个 `.fdf`，是 War3 的声明式 UI 布局。统计：

| Frame 类型 | 次数 | 属性（前几） | 次数 |
|---|---|---|---|
| `TEXT` | 737 | `SetPoint`（锚点） | 1172 |
| `BACKDROP` | 446 | `Width` / `Height` | 582 / 354 |
| `FRAME` | 202 | `Text` | 541 |
| `GLUETEXTBUTTON` | 165 | `BackdropBackground` 等九宫格 8 项 | 各 110–241 |
| `HIGHLIGHT` / `GLUECHECKBOX` | 72 / 62 | `FontColor` / `FrameFont` | 179 / 95 |

**技术上可行**：`FRAME`→`Control`、`TEXT`→`Label`、`BACKDROP`→`Panel`+`NinePatchRect`、
`EDITBOX`→`LineEdit`、`TEXTBUTTON`→`Button`，`SetPoint` 的四种写法能映射到 anchors + offset。

**但有三个坑**，工作量集中在它们身上：

1. `SetPoint TOPLEFT, "parent", TOPLEFT, x, y` 有 4 种参数形态，要按父级锚点换算偏移；
2. `Backdrop` 的九宫格是 `EdgeFile + CornerFlags + CornerSize + BackgroundInsets` 四组参数联动，
   和 Godot `NinePatchRect.patch_margin` 语义不完全等价，得先把贴图切成九宫格；
3. `DecorateFileNames` 表示 `File "ConsoleTexture01"` 是别名，真名在 `GlobalStrings.fdf` 里，要额外建一张别名表。

**结论：暂不转。** 理由不是难度，是**没有使用场景**——本项目的编辑器界面是自研的
Ribbon + ViewportPanel，不是复刻 War3 界面；74 个 fdf 里没有一个会被用到，
而且转出来的 `.tscn` 只有静态布局，按钮点击、菜单展开这些行为本来就不在 fdf 里。

真要做"War3 风格皮肤"时再转，建议先只转 `Glue/MainMenu.fdf` 和 `UI/ConsoleUI.fdf` 这两个做验证，
覆盖率能到 80%（静态部分），菜单/滚动条这类只保留外观。

导出配置：

```
export_filter="all_resources"            # 全量，单文件约 351 MB
include_filter="assets/terrain/*"        # 只补 SLK 这类非资源文件
```

**模型不靠枚举目录，直接拼路径。** 导出包里原始 `.glb` 不进 pck，只剩 `.glb.import` 注册和
`.godot/imported/xxx.glb-<md5>.scn` 实体，所以 `DirAccess.GetFilesAt("res://assets/converted/...")`
在打包环境下返回 **0 个文件**（开发态是 2043）。

`ModelLibrary.Find()` 因此只做一件事：把 `Doodads/Terrain/Cliffs/CliffsAAAB0` 拼成
`res://assets/converted/Doodads/Terrain/Cliffs/CliffsAAAB0.glb`，再用 `ResourceLoader.Exists` 判定存在性——
这条路在 pck 里是通的（`.import` 注册还在），只是目录枚举不通。

大小写写错时 `Exists` 返回 false，`CliffMeshFactory` 会把名字打进 `[CLIFF] 缺少模型: ...` 告警，
照着改常量即可。曾经试过生成 `_models.txt` 清单来规避，结论是**没必要**：
清单只是把「路径写错」变成「清单写错」，还多一个必须同步的派生产物，已删除。

重建顺序（三条命令，缺一不可）：

```bash
python tools/mdx2glb.py war3                                   # 模型：默认写 Godot/assets/converted
Godot.exe --headless --path Godot -- --image-convert="war3|Godot/assets/converted"   # 贴图
Godot.exe --headless --path Godot --editor --quit              # 导入（约 15 分钟）
```

验证：把导出的 exe 单独拷到空目录，`--map=` 打开 BootyBay，日志应为
`[CLIFF] 悬崖格 2400 个（其中斜坡过渡 20）` / `[MAP] 地表贴图 6/6 张` / `[MAP] 地面格抠掉 2413`。
同机位（`--cam=-21759,1551,9375`）与 HiveWE 的灰度差排除笔刷圈后 **0.53**。


产物（**场景不含任何脚本**，用 Godot 打开就能静态观察）：

```
Godot/Demo/
├── BootyBay.tscn                    12 MB，根节点普通 Node3D（scale = 0.01）
│                                    子节点 MapCliffs / MapTerrain / MapWater（ArrayMesh 内嵌）
├── shader/                          Demo 专用 shader（吃图集），和运行时那套分开
│   ├── terrain_map.gdshader
│   ├── cliff_map.gdshader
│   └── water_map.gdshader
└── BootyBay/
    ├── ground_material.tres         → Demo/shader/terrain_map + atlas/ground.res
    ├── cliff_material.tres
    ├── water_material.tres
    └── atlas/{ground,cliff,water}.res
```

几何**不是重写**：新增的 `ViewportPanel.BuildMapTree(terrain)` 内部依次调
`BuildMapCliffs → BuildMapTerrain → BuildMapWater`，和编辑器里跑的是同一套 1273 行代码。

**两套 shader 分开**：运行时用 `assets/shaders/`（`Texture2DArray`，一个材质采样全部图层），
Demo 用 `Demo/shader/`（竖向拼接的图集，`vec2(uv.x, (uv.y + layer) / layer_count)`）。
分开的原因是图集方案有 mipmap 跨层串色的隐患，不想让它影响编辑器；Demo 侧的实测差异可以忽略。

**根节点缩放 0.01**：War3 原生 1 格 = 128 单位，整张图 24576×12288，
在 Godot 3D 视口里比默认操作尺度大两个数量级——拖拽一像素对应的位移相对整张图不到 1%，
看着像「拖不动」，相机还得拉到三万单位外才能看全，深度精度也差。
缩 0.01 后是 246×123（1 格 = 1.28 单位），视口里恢复正常手感。
几何数据本身不动，只缩放根节点；shader 用 UV 和局部坐标，`unshaded` 光照不吃世界尺度，
所以画面和未缩放时逐像素一致（实测差 0.03）。

### 8.1 为什么 Demo 要用图集，而且存 .res

运行时那套 `Texture2DArray` 是**渲染资源，Godot 没有它的序列化器**——存成 `.res` 只剩尺寸元数据、
像素全丢（加载时报 `_create_from_images` / `img.is_null()`）。场景要「不运行也能看」，材质就必须自包含。

所以 Demo 侧改成 **竖向拼接的图集**：

| 组 | 层数 | 单层 | 图集 | .res |
|---|---|---|---|---|
| 地表 | 193 | 64×64 | 64×12352 | 4.2 MB |
| 悬崖 | 2 | 256×256 | 256×512 | 700 KB |
| 水面 | 45 | 128×128 | 128×5760 | 3.9 MB |

材质因此完全自包含：

```
shader = res://Demo/shader/terrain_map.gdshader
shader_parameter/ground_texture = res://Demo/BootyBay/atlas/ground.res
shader_parameter/ground_layers  = 193.0
shader_parameter/lighting_enabled = true
```

**图集存 `.res`（ImageTexture）而不是 PNG**：PNG 走 Godot 导入，默认 `compress/mode=2`（VRAM 有损压缩）
+ `fix_alpha_border`，颜色会变——实测和运行时的差从 0.14 涨到 **1.5**。`.res` 里是未压缩的
ImageTexture，一次导出就到位，也不用再跑一遍编辑器导入。

### 8.2 三个坑

| 现象 | 原因 | 处理 |
|---|---|---|
| 图层/图集存出来是 0 字节，`GetLayerData` 返回空 | **headless 用 dummy 渲染器**，纹理没有 CPU 数据 | 导出必须带渲染器跑，不能 `--headless` |
| 场景渲染比运行时暗/偏色（差 1.5） | 图集存成 PNG，Godot 导入默认 VRAM 有损压缩 | 改存 `.res`（ImageTexture） |
| 同机位截图对不上（差 36） | `LoadScene` 没走 `FrameCamera`，相机用字段初值（yaw 35°/pitch -46°/dist 2900），而地图取景是 180°/-56°/2560 | `LoadScene` 里补上同样的三个默认值 |

shader 里还有个语言细节：`UV` 是 `fragment()` 的内建变量，不能直接在普通函数里用
（会报 `Unknown identifier 'UV'`），要当参数传进去。

### 8.3 验证

|---|---|---|
| Demo 场景（图集 + 0.01 缩放）vs 运行时（数组） | 0.26 | **0.03** |
| Demo 场景 vs HiveWE | 1.03 | **0.38** |
| 运行时还原后 vs HiveWE（回归） | — | 0.54 |

| `--shot-water` | 同两张图 | IoU 100.0% / 平移 (0,0) 一致 |
| `--shot-mirror` | 同两张图 | 结论一致（无镜像） |
| `--crop` | 400,200,120×80 ×3 | 输出**逐像素相同** |
| `--w3e-probe` | x=60 剖面 7 点 + ramps 列表 | 高度逐点相同，83 个斜坡格相同 |
| `--draw-tiles` | 34~37 四条线 | 中间点差 ≤1px（float/double），线条形状一致 |
| `--paint-map` | Dungeon tileset 全量重写 | **逐字节相同**（131172 字节，md5 一致） |
| `--table-export` | 35 张表，比对生成内容 | 35/35 相同（13088 行） |
| `--text-export` | 98 张表，比对生成内容 | 99/99 相同（48848 键） |
| `--mdx-export` | 2043 个模型与旧产物对比 bin/accessor | bin 差 0.04%，1794/2043 完全一致 |

`--table-export` 比 Python 版多找到 2 张表（`AbilityMetaData` / `MiscMetaData`）：
它们的名字只在 `War3xlocal.mpq` 的 `(listfile)` 里，不在 `WAR3.MPQ` 的主 listfile。
现在 `War3Cli.AllNames` 会合并所有归档的 listfile。

`--mdx-export` 比 Python 版多转出 5 个模型（2048 vs 2043）：那 5 个是畸形 MDX，
Python 版越界抛异常，C# 版把越界读退化成默认值，能继续转完。

### 10.3 MDX 解析踩的坑（C# 版）

| 现象 | 原因 | 处理 |
|---|---|---|
| 1601/2048 个模型抛 `ArgumentOutOfRangeException` | 畸形记录的长度字段为负，把读取位置推成负数，`Latin1.GetString(index<0)` 直接抛 | `U32/I32/Floats/String/Tag` 全部加上下界判断，越界返回默认值（和 Python 切片行为一致） |
| 转换卡在第 158 个模型不动 | 子块长度 ≤ 0 时 `Position` 不前进，`while (Position + 8 <= end)` 原地打转 | `ReadNode/ReadMaterial/ReadGeoset` 三个循环记录入口位置，一轮结束没前进就强制 `+8`；主循环遇到 `size <= 0` 直接 break |
| 三角形只画出 1/3 | `indices` 的 accessor `count` 按「每 3 个索引 = 1 个元素」算错了 | accessor 的 `count` 是**元素个数**，索引的每个元素就是一个索引，`components` 传 1 |

## 11. 单位与物品显示

地图上摆放的单位来自 `war3mapUnits.doo`。这一轮做到「静态显示」：
**不播动画、不做阴影、不换队伍颜色**，和 HiveWE 的 StaticMesh 行为一致（它也只用第一帧的静态网格）。

### 11.1 数据链路

```
war3mapUnits.doo                      UnitUI.slk / ItemData.slk        assets/converted
  typeId + 位置/朝向/玩家   ──┐         file:    units\critters\Sheep\Sheep
                             └───────→  modelScale: 1.0            ──→  Sheep.glb
```

| 环节 | 位置 |
|---|---|
| doo 解析 | `Core/Formats/W3x/W3oUnits.cs` |
| 挂到地图文档 | `MapDocument.Units`（按 ItemData/UnitData 表区分单位与物品） |
| id → 模型 | `Game/Assets/UnitMeshLibrary.cs`（单位查 `UnitUI`，物品查 `ItemData`） |
| 实例化 | `ViewportPanel.BuildMapUnits` |

坐标换算（已核对）：`格 = (doo 的 x,y − terrain.offset) / 128`，
Godot 位置 = `(-(x-offsetX), z, y-offsetY)`；朝向 `rotation.Y = π + angle`
（地形的 x 取反相当于整体绕 Y 转了 180°，朝向要补这个角）。

### 11.2 doo 的记录是变长的

`war3mapUnits.doo` 的单位记录长度不固定，必须按顺序读完才能算出下一条的起点：

```
id(4) variation(4) position(12) angle(4) scale(12)
flags(1) player(4) unknown(2) health(4) mana(4)
[v8] itemTablePointer(4)
itemSets: 数量 + 每个 set 的（数量 + 数量×8）
gold(4) targetAcquisition(4) level(4)
[v8] 力量/敏捷/智力(12)
背包: 数量 + 数量×8
技能: 数量 + 数量×12
randomType(4): 0→4B、1→8B、2→（数量 + 数量×8）、其它→不占
customColor(4) waygate(4) creationNumber(4)
```

有两个容易踩的点：
- `randomType == 0` 也要读 4 字节（HiveWE 的 `case 0` 分支），漏了会整体错位 4 字节
- 这个文件里有 `randomType == 0xFFFFFFFF` 的记录（表示没有随机单位），不能按 0/1/2 之外就报错

`--unit-dump=地图` 会把版本、单位/物品数量、类型分布、全部坐标打出来，改解析时先用它核对。

### 11.3 这一轮修掉的两个 bug（影响全部 2048 个模型）

| 现象 | 根因 | 修法 |
|---|---|---|
| 村民的身体用了「血」贴图（`gutz.blp`），整个模型是彩色噪点 | **`LAYS` 块头第二个字段是「层数」，不是字节长度**。原来把 1 当长度，`body + length` 直接错位，`filterMode`/`textureId` 全部读到了错误的字段 | `LAY S \| count \| layer[count]`，每层以 inclusiveSize 开头（28 字节 + 贴图动画子块），按层大小逐层跳 |
| 羊身上散布黑色噪点，不像 HiveWE 那样干净的白身黑头 | **`filterMode` 映射全错**：1~6 全当成 BLEND。实际 1 = 透明镂空（alpha test 0.75），2 = 半透明，3~6 是加法/调制 | 0→OPAQUE、1→MASK(cutoff 0.75)、2→BLEND、3-6 暂退化成 BLEND（glTF 无加法混合，做特效时再处理） |

改了转换器就要重跑 `--mdx-export` + 重新导入。导入 2048 个 glb 约 **26–36 分钟**，
中途可能在 88% 附近段错误（消息队列溢出），**再跑一次增量导入即可完成**。
