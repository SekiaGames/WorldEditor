# 重构原则

## 一条判据

以客户端实现为唯一基准。Launcher 侧保留的差异只有一类：本地运行所需的载入与表现——pck 里的 Godot 美术资源、C# 表配置、Godot 渲染节点。这些是同一份逻辑的本地形态，不是另一套逻辑。

## 搬运方式

1. **有等价实现就删**。删 Launcher 的类，在装配表里给它原来的能力代码加别名，指向客户端实现。重写一份等于制造第二个基准。
2. **同机制不同代码就合并**。同一个原生模板的多个代码共用一个实现（`AHdr` 与 `ANdr` 都指 `RuntimeDrainAbility`）。
3. **同族机制就照该族写**。客户端没有该代码但存在同族实现时，按最接近的那个类逐行对着写——字段读取、时序、命名、生命周期挂点全部跟随。引导型看 `RuntimeDrainAbility`，单体/范围伤害型看 `RuntimeFrostNovaAbility`。
4. **纯数据保留，入口改注入**。表与规则类可以留，但不能自己读盘，必须走装配层注入的实例（`AbilityCatalog.Objects`、`UnitFactory.Objects`）。
5. **JASS 依赖换等价模型**。客户端里依赖 JASS 层的部分，用 Launcher 侧等价模型承接（可破坏物用 `TreeState`），承接不了的整体不移植。

## 不自创

自创是偏差的唯一来源。以下四类最容易出事：

**坐标**。模拟层只有 `Vec2`，跟随客户端。三维坐标由地形高度与飞行高度推导，仅供表现层使用。一旦再存一份 `Vector3` 作为真值，两份就会漂移。

**玩家**。客户端只有 `PlayerId` 与查询委托。需要玩家对象时，由模拟层持有最小状态（经济、补给、种族），不复制客户端的 JASS 玩家表。

**字段名**。物编列名一律从客户端的读取点反查（`UnitFactory.TypeData.InitializeTypeStats` 是权威来源），不按 WC3 习惯拼。猜错的后果是编译通过、数值全错——比编译错误更难查。

**时序**。施法、引导、buff 生命周期按客户端挂点组织，不把 Launcher 自己的 tick 语义带进来。例如 buff 存活判定归 `Duration`，`OnTick` 就只做每个 tick 的工作。

## 判定方法

- **判重看能力代码，不看类名或文件名**。`Bladestorm` 与 `WhirlWind` 都是 `AOww`，按名字永远对不上。
- **删文件前查调用者**。转发性质的成员集合常被上万处引用，看着像重复桩，删了就是全仓断裂。
- **代码字面量扫不到时按语义对**。`Web` 对应 `Aweb`、`MassDispel` 对应 `Adis`，文件里未必出现代码本身。
- **能力代码第二字符可能小写**（`Agyd`/`Amin`/`Achd`），匹配模式要放宽，并且要扫全文而非文件头。

## 遮蔽陷阱

CS0102 / CS0111 这类重复定义会让编译器**停止分析该类型的其余成员**。表现是错误数骤降，像进展，实际是视野被切断。

- 看到错误数突然下降，先确认不是遮蔽，再查语法错误（表达式体写成 `= new X{}` 会让整文件解析失败）。
- 解除遮蔽后数字暴涨是正常的，按根因归并——几千条往往只有一个成员缺失。
- 一个类型只允许一份定义；补投影成员前先确认它是否已存在于别的分部类。

## 进度口径

错误数不是进度指标，根因数才是。一万条 `Unit 未包含 Position` 是同一个根因；一条 `UnitTypeData` 列名写错却是真正的风险。
