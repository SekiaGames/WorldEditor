## 导出包（单文件 exe）悬崖全丢：glb 索引 0 个

3. `export_presets.cfg` 的 `include_filter` 加 `assets/models/_index.txt`

**教训**：凡是靠「扫目录」找资源的地方，导出包里都会归零；要用清单或 `ResourceLoader.Exists`。

## 纠正：`_models.txt` 清单是多余的，改回直接拼路径

`export_presets.cfg` 的 `include_filter` 回到 `assets/terrain/*`；删除 `converted/_models.txt`。

**验证**（空目录跑导出 exe）：`悬崖格 2400 / 斜坡过渡 20 / 地表 6/6 / 抠掉 2413`，

## Demo 阶段：导出 BootyBay.tscn

新增 `--export-scene=地图|场景`，产物：
```

Godot/Demo/BootyBay/{ground,cliff,water}_material.tres   ← 材质球

```

**几何复用 `ViewportPanel.BuildMapTree(terrain)`**（新加）：内部就是 BuildMapCliffs → BuildMapTerrain
→ BuildMapWater，和编辑器里跑的是同一套 1273 行代码，不是重写。

**踩到的三个坑**：
1. `Texture2DArray` **存不进资源**：它是渲染资源，Godot 没有序列化器，存 .res 只剩尺寸、像素全丢，
   加载时报 `_create_from_images` 失败。改成把每层导出成 PNG，场景脚本运行时拼回数组。
   → 因此导出要跑两次：第一次写 PNG，等 `--editor --quit` 导入后再跑一次，.tscn 才带贴图引用。
2. **`Node3D.SetScript()` 会重建 C# 实例**，之后手里的 `root` 句柄失效（`ObjectDisposedException`）。
   改成直接 `new BootyBayScene()` 当根节点，再把子节点搬过去，属性直接赋值。
3. **headless 拿不到纹理像素**：`GetLayerData` 在 dummy 渲染器下返回空，导出必须用带渲染器的模式跑。

**图层数量**（之前理解错了）：地表 array 是 **193 层 64×64 小瓦片**（6 张 512×256 图集 × 8×4
= 192 + blight 1），不是 6 层；悬崖 2 层、水面 45 层。

**相机**：`LoadScene` 要补 `_dist=20*CellSize / _yaw=180 / _pitch=-0.977rad`，
否则用字段初值（35°/-46°/2900）算出来的同机位差一截。

**验证**：`--scene=res://Demo/BootyBay.tscn --cam=-21759,1551,9375` 截图，
与运行时构建排圈差 **0.07**，与 HiveWE 排圈 **0.44**（比运行时的 0.53 还低）；`[DEMO]` 日志确认
193/2/45 张图层合入材质。

## 17:30 修蒙皮/材质：MDX geoset 三个 bug

用户反馈「蒙皮怪物模型有问题」。定位到三处，全部在 MDX→glb 转换里，**跟 Demo 场景无关，运行时同样烂**：

1. **`MTGC` / `MATS` 语义读反**。实测 4 个原始 mdx（ForestTroll/Gnoll/Footman/Sheep，19 个 geoset）都满足
   `sum(MTGC) == len(MATS)`：`MTGC` 是每组包含的骨骼**个数**，`MATS` 是展平的骨骼 objectId。
   旧代码把 MTGC 当骨骼 id、把 MATS 第一个值当材质号 → 每个顶点被绑到「编号=组大小」的骨头上，
   组内多骨骼均分权重也从没实现 → 模型被拉成尖片。
2. **材质号取错**。真正的 `materialId` 是紧跟 MATS 数据的裸 uint32（不是 UVBS 之后）。
   旧代码用 MATS[0]，抽查 19 个 geoset 里 16 个取错。
   修法：MATS 存 `MatrixIds`，接着读 materialId；去掉 MATS 里的 `continue`，让它落到下面「按标签找 UVBS」的分支。
3. **逆绑定矩阵平移写错列**。glTF 的 MAT4 列主序，平移在第 4 列（12/13/14），旧代码写到 3/7/11 → Godot 读出的平移全是 0。
   另外 `worldOffset` 单趟遍历依赖父节点 objectId 更小，改成带记忆的递归。

## 21:30 动画只有 Stand 正常的根因：节点 track 字段错位一格

用户反馈：Gnoll.tscn 里 Current Animation 播 Stand 正常，Attack/Death/Walk 都不对。

**根因**：`MdxModel.ReadNode` 把 track 子块的第二个 u32（`nbKeys`）当成 `length`（块字节数），
于是 `ReadTrack` 又从下一格读到 `count = interp`（取值 1/2/3），**每条轨道只读 1~3 个关键帧**，
且 key 的起始位置也偏了 4 字节。真实结构：
`KGTR | nbKeys | interp | globalSeqId | keys`（key = frame + value + 仅 interp>1 时带两组切线）。
同一个字段在 `GEOS`/`ATCH` 上是块字节数，在 track 上是关键帧个数。
Stand 看起来"正常"只是因为呼吸动作幅度小，前 3 帧恰好够骗过眼睛。

修法：`ReadNode` 用 payload 区分——track 分支交给 `ReadTrack(reader, width, count)`（读 interp + gsid + count 个 key），
GEOS/ATCH/未知分支仍按 `body + payload` 跳过。`ReadTrack` 里 count 用 `Math.Clamp(count, 0, 1<<16)`。

**实测**（Gnoll，38 条轨道）：
| 动画 | 关键帧 | 长度 | 循环 |
|---|---|---|---|
| Stand | 99 | 1.000 | 是 |
| Attack - 1 | 187 | 0.833 | 否 |
| Walk | 260 | 1.066 | 是 |
| Death | 303 | 2.333 | 否 |
修复前每条轨道 ≤3 帧。`Gnoll_anims.tres` 133 KB → 243 KB。

**连带两处修复**：
1. `SelectKeys`：窗口内无关键帧时原来会用「下一个动作的首帧」做线性插值，导致整段动作朝别的动作漂移。
   改成保持「进入这个动作前的最后一帧」（start/end 两个同值 key）；窗口内有 key 但首帧晚于 start 时，补一个起点。
2. `LoopMode`：只有 Stand*/Walk* 循环，Attack/Death/Decay 停在最后一帧。

运行时验证：bone1/bone5 的姿态在 8/30/55 帧持续变化，player.pos 递增。

## 23:40 全量导出后抽查：建筑被整个隐藏（GEOA 两个 bug）

第一轮全量导出完成（2048 glb / 2048 tscn / 1062 anims / 895 tree / 3746 材质，失败 0），
但抽样发现 **TownHall 36 个 geoset 全部 `visible = false`**，建筑会完全消失。

**bug 1**：`ReadGeosetAnimation` 的 KGAO 关键帧没跳过切线。`interp > 1` 时每帧是

Gnoll 的 KGAO 恰好是 linear（无切线）所以之前没暴露。修法：按 interpolation 跳过 2 个 float。

**bug 2**：判定点不可靠。建筑的 KGAO 描述的是「建造 / 升级」过程，在 `Stand` 起点上
TownHall 是 0/36、GryphonRider 是 2/12。修法（两条兜底）：
- `hiddenGeosets.Count == Geosets.Count`（全隐藏）→ 清空，全部显示
- 被隐藏的顶点数超过总共 60% → 同样清空

实测：TownHall 0 隐藏、Gnoll 4 隐藏（尸体/血雾/TeamGlow）、GryphonRider 10 隐藏（都是 4~56 顶点的小块，

## 07:50 导出包里中立野怪消失：资源路径大小写

用户报 `WorldEditor.exe` 打开 BootyBay 没有中立野怪。**开发环境正常**（食人魔、地精商店都在），

**根因**：`UnitUI.slk` 的 file 字段是全小写（`units\creeps\Gnoll\Gnoll.mdx`），

编辑器在 Windows 上不区分大小写所以一直没事（那些 `Case mismatch opening requested file` 警告就是这个），
但 pck 里路径**严格匹配**，`ModelLibrary.Find` 直接拼路径必然 miss，单位被跳过。

**修法**：`ModelLibrary.Find` 改三级查找 —— 精确 → 首字母大写猜测（`units/x` → `Units/x`）→
`DirAccess` 逐段不区分大小写枚举。MPQ 目录规律是首字母大写，抽样 4 条路径全部命中，
第 2 步即可覆盖全部模型。**不需要重跑模型导出，只需重新打 exe**。

附带：`WorldEditor.exe` 的内嵌 pck 目录表是加密的（`pack_flags` 含 bit1），python 解不出文件列表，
只能靠运行日志判断。
